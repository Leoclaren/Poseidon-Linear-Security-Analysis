# Research Plan — Lightweight & Algebraically-Robust Linear Layers for Poseidon-family Permutations

Target venue: **IEEE S&P 2027**
Branch: `new_iteration`
Last regenerated: 2026-11-02, after reading the full PDFs of both primary attack papers (`2026-306.pdf`, `2026-1579.pdf`, now in the repo root).

## 1. Problem statement

The original claim in this repo (`CLAUDE.md` / `AGENTS.md`) is that a non-MDS matrix in Poseidon1 partial rounds is unsafe, and MDS fixes it. That is correct but **not sufficient** as a 2027-grade security argument: MDS only rules out the *infinite* invariant subspace trail. Two 2026 papers show that **properly-MDS matrices can still be made unsafe**, through two distinct mechanisms (full detail in §3):

- **Vitto (2026/1579):** every linear layer admits *unavoidable finite* subspace trails; if the matrix is chosen *after* the round constants are fixed, an adversary can steer a constrained input family through the initial full rounds and into that unavoidable trail ("full-round absorption").
- **Merz & Rodríguez García (2026/306):** Poseidon2(b)'s efficient Kronecker-structured external-round matrix has unconstrained low-weight eigenvector subspaces, independent of the (already-vetted) internal-round matrix.

Neither attack breaks the claimed 128-bit security of a standard, properly-generated parameter set — and, importantly, **each paper already names a concrete, essentially-free countermeasure**. So the open problem is not "patch one more attack." It is:

> **Formalize one general, automatable criterion — covering infinite trails, finite/full-round-absorption trails, and tensor-structure round-skipping — that any candidate `(α, R_F, R_P, M)` can be checked against, apply it to find the lightest parameter set that passes, and benchmark that set with real constraint counts against the current efficiency state of the art (Polocolo, Anemoi).**

That generalization — not either individual patch — is the paper's contribution.

## 2. Objectives

1. **Resistance** — one criterion that rules out: (a) infinite invariant subspace trails, (b) finite-trail reachability via full-round absorption, (c) tensor-structure round-skipping, (d) anomalous Gröbner/resultant degree drop. Prefer proof over empirical survival; where proof isn't reachable, report the adversarial falsification effort explicitly.
2. **Lightweight** — satisfy (1) at minimum arithmetization cost (R1CS constraints / custom-gate degree, measured, not asymptotic).
3. **Joint, not sequential** — both objectives share the same knobs `(α, R_F, R_P, structure of M)`; solving them in sequence ("secure first, then shrink") risks the lightweight pass silently reopening an attack. Score every candidate on both axes at once.
4. **Honest benchmarking** — compare against Poseidon, Poseidon2, Poseidon2b, *and* the current efficiency leaders (Polocolo, Anemoi), with real constraint counts.

## 3. Threat model

| # | Attack | Mechanism | Known countermeasure | Repo status |
|---|---|---|---|---|
| 1 | Infinite invariant subspace trail | `B(M) < t+1` (non-MDS) lets a coordinate subspace stay invariant forever, so the S-box never engages | MDS (`B(M) ≥ t+1`) + irreducible `χ(M_W)` (**GRS21**) | ✅ `analysis/subspace_scanner.py` (Algorithm 1) |
| 2 | Gröbner basis cryptanalysis via subspace trails | Low-degree Gröbner basis computable along a known trail | Keep trails short / break them structurally | ⚠️ partial (`attacks/security_proof.py` only covers #1) |
| 3 | Finite subspace trail + full-round absorption, **under adaptive matrix choice** | Finite trails (`dim K_r(M) ≥ t−r`) are unavoidable for *every* linear layer — not itself a flaw. The flaw: if `M` is chosen after the round constants are fixed, a constrained input family can be steered through the initial `R_F/2` full rounds into that trail. Vitto: degree `3^10` vs. expected `3^28` on `(t,α,R_F,R_P)=(16,3,8,20)`; complete CICO-2 solution. Necessary condition for the balanced construction: `R_f(k+1) ≤ t`. | **Bind round constants to the matrix**: derive constants as a hash of a canonical encoding that includes `M` (Vitto §6.3) — zero extra cost, kills the adaptive-choice premise entirely | ❌ to build (§5, Phase 1/2) |
| 4 | Round-skipping via Poseidon2(b)'s tensor-structured external matrix | `M_ε = P_{t/4} ⊗ M_4` has low-weight `{1,−1}` eigenvectors → unconstrained `(X,−X)` subspaces surviving full rounds at zero degree cost. Claimed the largest CICO-2 bounty in Ethereum's Poseidon initiative in <11h/64 cores (vs. 40h/1000 cores previously). First example of preimage easier than CICO; first collision attack beating preimage (2^106 improvement, one 128-bit parameter set). | **Swap the Kronecker factor order**: `M̄_ε = M_4 ⊗ P_{t/4}` — identical multiplication cost, defeats every round-skip in the paper when `c ≥ t/4` or `d ≥ t/4` (true for all recommended sets) | ❌ to build (§5, Phase 1/2) |
| 5 | S-box skipping (generalization of #4) | — | TBD | ❌ watch for scope overlap, eprint 2026/1692 |
| 6 | Bivariate resultant attacks, round-reduced | Improves degree/complexity bounds for resultant solving | Keep algebraic degree margin | ❌ relevant to objective 1(d), eprint 2026/1905 |
| 7 | Kleptographic ("nothing-up-my-matrix") backdoors | Adversarially-chosen matrix hides a weakness while passing standard checks | Same fix as #3: generation must be non-adaptive / transcript-committed | ❌ same fix as #3, eprint 2026/1901 |

Both #3 and #4 are narrower than their abstracts suggest and **neither is an attack on a fixed, honestly-generated standard instance** — both are about what becomes possible when a matrix is *searched for* against fixed constants. That is directly relevant to us: **our own Phase 2 matrix search is exactly that scenario**, so the countermeasures above must be built into the search procedure from the start, not bolted on after.

## 4. The unifying criterion (the paper's actual contribution)

Both known countermeasures (bind-constants-to-matrix; swap-Kronecker-order) are observed empirically by their respective papers to defeat the *specific* construction shown — neither paper proves a general theorem ruling out every attack of that shape. Our contribution is to state and check one criterion that subsumes both:

> For a candidate `(M_I, M_ε-or-M, generation procedure)`, does any proper subspace of the full-round matrix's eigenstructure survive into the partial rounds **without being constrained by the generation procedure**?

- Vitto's "domain–image relations" (full-prefix reachability) and Merz & García's `(X,−X)` eigenvector subspaces are two instances of this one question, differing only in *which* matrix (`M_I` vs. `M_ε`) and *which* round segment (partial vs. full) the unconstrained subspace survives through.
- A `(matrix, constants)` pair that passes this unified check is protected against both known attack classes, and — pending Phase 3's adversarial falsification — plausibly against future attacks built the same way.
- This is what `analysis/finite_trail_scanner.py` (§5, Phase 1) implements, and what every candidate generated in Phase 2 gets screened against before it's allowed into the efficiency comparison.

## 5. Experimental phases

**Phase 0 — Replication.** Reproduce Vitto's exact degree collapse (`3^28` expected vs. `3^10` achieved, same `(t,α,R_F,R_P)`) and Merz & García's tensor-structure round-skip (build `M_ε`, exhibit the `(X,−X)` subspace, confirm the swapped order kills it) in our own code. Required evidence that we understood the attacks before proposing a fix.

**Phase 1 — Algorithm 2 (`analysis/finite_trail_scanner.py`).** Implement §4's unified criterion: full-round reachability of a finite trail (generalizing Vitto), plus unconstrained low-weight eigenvector detection in the full-round matrix (generalizing Merz & García). Output a quantitative margin (trail dimension, rounds needed), not a binary verdict.

**Phase 2 — Lightweight matrix search (`poseidon/matrix_search.py`).** Generate candidates (Poseidon2-style sparse `M_I`, low-weight circulants, tensor-structured `M_ε` with the correct factor order) via **matrix-and-constants bound together from one seed** (§4's fix, applied by construction, not as an afterthought). Score each on: branch number, Phase 1's criterion, degree-bar growth through full rounds, and real arithmetization cost. Output: a cost-vs-security-margin table.

**Phase 3 — Adversarial falsification.** For every criterion conjectured in Phase 1/2, attempt to construct a counterexample (brute force for small `t`, SAT/SMT via Z3 if it scales). Record every attempt, successful or not — a documented failed attack is itself evidence for the paper.

**Phase 4 — Real lightweight benchmark.** Implement the 2–3 shortlisted candidates in circom (R1CS constraint counts) — escalate to Rust/arkworks or Halo2/plonky2 only if proving-time numbers are needed. Compare against published Poseidon, Poseidon2, Poseidon2b, **and Polocolo/Anemoi** (current efficiency SOTA, not just Poseidon).

**Phase 5 — Write-up.** Formal statement of §4's criterion + adversarial validation (Phase 3) + efficiency table (Phase 4), positioned explicitly as closing the gap Vitto 2026/1579 and Merz & García 2026/306 leave open, and matching/beating Polocolo/Anemoi on cost.

## 6. Lightweight design space

Cost model (to implement literally in `poseidon/matrix_search.py`):

**Corrected during Step 3.2 (poseidon/matrix_search.py)**: these are two separate numbers, not one. In R1CS, multiplying a wire by a *public constant* (every matrix entry) is a free linear combination — the linear layer costs zero R1CS constraints, confirmed empirically in Step 3.4 (`r1cs_constraints` came out identical across three very different matrices).

```
cost_r1cs(R_F, R_P, t, α)   =  R_F · t · constraints_per_sbox(α)     # full rounds: all t lanes nonlinear
                              + R_P · constraints_per_sbox(α)        # partial rounds: 1 lane nonlinear
                                                                      # (linear layer: 0 R1CS constraints)

mul_complexity(M)            =  count of entries not in {0, 1}       # per application of M;
                                                                      # real cost for native eval / Plonkish
                                                                      # custom-gate width, NOT R1CS
```

### 6.1 Within Poseidon's own design space (cheapest)

1. **Cut `R_F`, not `R_P`.** Full rounds cost `t` nonlinear lanes vs. `1` for partial — if §4's criterion proves security at a smaller `R_F` than Poseidon1's conservative `r_f=8` default, that's free once proven.
2. **Sparse `M_I`** (Poseidon2-style near-identity + low-rank row, already in `poseidon/matrices.py` as `poseidon2_style_matrix`): `O(t²) → O(t)` per partial round. If paired with a tensor `M_ε`, the factor order must be `M_4 ⊗ A`, not `A ⊗ M_4` (§3 row 4's fix), by construction.
3. **Lower S-box degree `α`** where `gcd(α, p−1)=1` and the new criterion still holds at the resulting `R_P` — lowers R1CS constraint *degree*, which Plonkish backends often charge for directly.
4. **Re-derive `R_P`** from the new combined criterion instead of reusing Poseidon1's formula (calibrated only against attacks #1–#2).
5. **Precomputed/optimized linear-layer decomposition** (the official Poseidon reference-implementation trick: one dense multiplication paid once, the rest sparse + pushed-forward constants) — zero security impact, verify candidates still admit it before claiming raw multiplication counts.
6. **Round-varying / rotating S-box lane** (novel, higher risk, needs Phase 3 before relying on it) — a static trail needs the *same* coset to survive every round; varying the matrix or the active lane per round (NUMS-derived) could cut `R_F` further, in the spirit of GMiMC's round-varying linear layers. Cuts both ways — Vitto's own attack *is* a round-constant-dependent matrix — so this must be adversarially tested, never assumed safe.

### 6.2 Cross-family techniques worth importing

None of these were vetted against §4's criterion — importing one means re-running Phases 1–3, not copying published round numbers.

- **Anemoi** (Bouvier et al., eprint 2022/840) — Flystel S-box, 21–35% fewer Plonk constraints than optimized Poseidon; its `Jive` mode is a direct comparison point for our mode choice.
- **Griffin** (Rescue-Prime lineage) — quadratic nonlinearity, sequential state processing.
- **Polocolo** (Ha et al., eprint 2025/926, EUROCRYPT 2025) — current efficiency SOTA: 21% fewer gates than Anemoi (`t=8`), 24% fewer than Reinforced Concrete (`t=3`), via power-residue S-box. **This is the benchmark to beat in Phase 4.**
- **Reinforced Concrete** (CCS 2022) / **Monolith** — lookup-table S-box instead of a low-degree polynomial. Structurally interesting for Objective 1: subspace-trail and Gröbner attacks are attacks on *polynomial* structure, and a lookup has no algebraic degree to track. Candidate experiment: a hybrid permutation — mostly cheap algebraic partial rounds, a handful of lookup-based rounds to break any residual trail instead of paying for more full rounds. Only applies on lookup-argument backends (Halo2/Plonky2/STARK), not plain R1CS.

### 6.3 Mode- and field-level efficiency

- **PA / PAX compression modes** (Trevisani et al., eprint 2026/1271) — up to 2× over Sponge in software, 10% faster Groth16 circuits, 60% faster in Plonky2; stacks on top of whichever permutation we pick. New enough (2026) to need its own check against our threat model before adopting.
- **Smaller native fields** (eprint 2025/1593) — match the field to the proof system's native arithmetic (Goldilocks/BabyBear/KoalaBear). Caveat: Vitto's strongest result is on a KoalaBear-sized instance, so smaller fields couple security margin to field size — re-validate §4's criterion per field, don't assume it transfers from BN254-scale analysis.

### 6.4 Synthesis

Every lever above feeds one table: candidate `(α, R_F, R_P, M, S-box family, mode, field)` tuples, each scored pass/fail on §3's threat table and a real constraint count against Polocolo. That table is the paper's main result.

Fixed by reusing Algorithm 1's general technique (`ker(f_i(M))` for every irreducible factor `f_i` of `χ(M)`, not just linear ones) applied to the *full* matrix.
  - **Second, more interesting finding, also found empirically**: even with the fix, a *dimension/weight*-only threshold still could not tell `M_ε` from `M̄_ε` apart — both have identical eigenvalues **and** identical weight distributions (permutation-similar matrices preserve both). Printed the actual zero positions: `M_ε`'s weight-8 eigenvector has zeros at the *contiguous* block `[8..15]`; `M̄_ε`'s weight-8 eigenvector has zeros *scattered* at `[2,3,6,7,10,11,14,15]` — same count, no long contiguous run. This is exactly Merz & García's own stated reason the swap works ("incompatible with constraints on every fourth element"). Rebuilt the check around `max_contiguous_zero_run` instead of raw weight/dimension — **now correctly distinguishes them**: `M_ε` → `any_suspicious=True`, `M̄_ε` → `any_suspicious=False`, matching Step 1.4 exactly, via a general algorithm that never saw the Kronecker structure.
  - **Known limitation, documented in the code, not hidden**: the default `suspicious_run_threshold = t//4` is Merz & García's own CICO-`c`/`d ≥ t/4` criterion, meaningful for Poseidon2(b)'s quadruple (`t` divisible by 4) design. At `t=3` (this repo's Poseidon1-style default) it rounds down to a degenerate threshold of 1, flagging nearly any structural zero — not wrong, just overly conservative outside the regime it was calibrated for; callers targeting a specific `CICO-k` should pass an explicit threshold.
  - **Scope note**: the *reachability* half of Vitto's mechanism (does some adversarial `M_I`/constants pair actually place a family inside a finite trail via the full-round prefix) is still **not** attempted generically here — per Step 1.2's scope note, that is Phase 3's adversarial-search job, not a static scan. What's built here is the static *structural* half of Sec 4's criterion for both known attack classes.

### Step 5.4 — "Is there a way to make it lighter?" (2026-11-03, prompted directly by the user after Step 5)

Tested the most intuitive lever first and it **failed**: lowering `α` from 5 to 3 at `t=3` requires `R_P` to grow from 56 to 83 (real published numbers, SoK eprint 2026/1931 Table 5a), and the extra rounds' linear-constraint overhead (`cost_r1cs_linear` scales with `R_P·(1+t)`) more than cancels the per-S-box saving — **594 total R1CS constraints vs. 512 at α=5**, confirmed by a real `circom` compile, not just the formula. Lowering `α` makes this design *heavier*, not lighter, in R1CS.

The lever that actually works: **smaller native field.** Until now every module in this repo hardcoded the BN254 prime (`poseidon/field.py`'s module-level `P`). Generalized it: `poseidon/field.py` now exposes `make_field(prime)` plus ready-made `FpKoalaBear` (2^31−2^24+1) and `FpGoldilocks` (2^64−2^32+1) classes; `poseidon/linalg.py`, `poseidon/polynomial.py`, `poseidon/matrices.py`, `poseidon/constants.py`, `poseidon/matrix_search.py`, and `analysis/subspace_scanner.py` were all updated to infer the field from the data they're handed (`type(x)`) instead of importing the global `P`, so the exact same code now runs over any prime, zero-regression-risk (BN254 remains the untouched default everywhere).

**First pass result** (since corrected, see below): at `t=3, α=3, R_F=8, R_P=20` (reusing the public KoalaBear instance's own round count, conservative for `t=3` since the published number is for `t=16`) over `FpKoalaBear`: predicted and `circom`-verified (both bn128-structural and real `--prime goldilocks` arithmetic) **88 non-linear + 128 linear = 216 total constraints**.

**Correction found immediately after, while building the R_F statistical-security checker this same step (see §5.5 below): `R_F=8` was reused from the published `t=16` instance without re-deriving it for `t=3` — unsound.** The original Poseidon paper's own statistical-security bound (eprint 2019/458 Eq. 2) depends on `t` through a `(t+1)` factor in its threshold; re-deriving it properly for `t=3` at KoalaBear's field size gives a required `R_F=12`, not 8 (full derivation in §5.5). Re-ran with the corrected `R_F=12`: **112 non-linear + 152 linear = 264 total constraints**, confirmed again by a real `circom --prime goldilocks` compile. Still a real win — **~1.9x fewer constraints than the BN254 baseline (512-519)**, just smaller than the uncorrected 2.4x first claimed.

**The honest caveat, stated plainly**: this is a deployment decision, not an algorithm improvement — it only applies if whatever this permutation needs to interoperate with doesn't require BN254/Groth16 specifically (e.g. an existing Ethereum/BN254-anchored system). Candidate security checks (Algorithm 1 + 2, `unified_criterion`) all passed over `FpKoalaBear` with no changes needed — the same NUMS generation and unified criterion work unmodified over the new field, which is itself a useful confirmation that the tooling built in Steps 2-4 wasn't accidentally BN254-specific. **Second caveat, the one that bit us here**: `R_P`/`R_F` published for one `(t, field)` pair do NOT transfer to a different `t` at the same field without re-checking — our own tooling (Algorithm 1/2) doesn't check statistical security at all, so this kind of mistake is exactly what §5.5's new checker exists to catch going forward.

### Step 5.5 — The other pending lever: can `R_F` itself be cut below 8? (2026-11-03)

Built the checker that was missing (flagged as a gap at the end of the previous "no existe manera de hacerlo mas ligero" exchange): fetched the real USENIX Security 2021 PDF of the original Poseidon paper (eprint 2019/458) directly — WebFetch's text extraction failed on it (binary/compressed stream), but the harness still saved the raw PDF locally, and it read fine with the PDF-page-image reader — and transcribed **Eq. (2)** exactly, the actual statistical (differential/linear) security bound that lower-bounds `R_F`, independent of and *not covered by* any of our algebraic subspace-trail tooling (Algorithm 1/2 only ever checked the algebraic side):

```
R_F < 6   if M <= (floor(log2(p)) - C) * (t + 1)
R_F < 10  otherwise
```
`C = 2` for `S(x)=1/x`, `C = log2(alpha-1)` for `S(x)=x^alpha` (`C=1` for `alpha=3`, `C=2` for `alpha=5`); final `R_F` = this bound + the paper's own arbitrary `+2` margin (Sec 5.4). Implemented in new `poseidon/round_numbers.py::statistical_min_R_F`.

**Validated against the paper's own worked examples before trusting it on anything new**: reproduces `R_F=8` exactly for all three of Propositions 5.1/5.2/5.3 (Poseidon-80/128/256, BN254-scale, `α=5`) — matching Table 1 — and also reproduces `R_F=8` for the public `t=16` KoalaBear instance Vitto/the Initiative actually use. Only then applied it to our own candidates, where it caught the Step 5.4 error above.

**Answering the actual question ("can we cut R_F below 8 at BN254?")**: no — at `t=3, α=5` over BN254 (`log2(p)=255`), the threshold `(255-2)·(3+1)=1012` comfortably exceeds `M=128`, landing in the `bound=6` branch — `6+2=8`, exactly our existing default. There is no slack to cut at our current `(t, field, α)` point; `R_F=8` is already the (margin-inclusive) minimum the original paper's own formula requires, not an arbitrarily conservative legacy number. The lever would only open up at a different `(t, field)` combination where the `(t+1)` factor pushes the threshold comfortably above `M` while still using a small field — exactly the KoalaBear-at-larger-`t` regime the public instance already lives in, not something our own BN254-anchored default can exploit further.

### Step 5.6 — Rotating the active S-box lane (user's idea, 2026-11-03): double-edged, no net win for our candidates

§6.1-6 flagged "vary which lane carries the partial-round S-box instead of always coordinate 0" as a candidate idea, never tried. Tested it directly by generalizing `finite_trail_space` (Step 1.3) to `finite_trail_space_sequence(M, active_coords)` — same construction, but each round's constraint comes from the row of `M^j` matching that round's ACTIVE coordinate instead of always row 0. `active_coords = [0]*r` reproduces the original exactly (regression-checked).

**Result at `t=3`, comparing fixed (`[0,0,0,...]`) vs. rotating (`[0,1,2,0,1,2,...]`) schedules:**
- `mds`, and our actual NUMS `poseidon2_sparse` candidate: **identical dimension decay either way** (`[3,2,1,0,0,...]`) — both already hit the theoretical ceiling (dimension can only drop by 1 per added linear constraint, "maximal partial-round rank growth"), so rotation has literally nothing to improve for a matrix that's already good.
- `identity` (the known infinite-trail-vulnerable matrix): rotation **fixes it for free** — `[3,2,2,2,...]` (infinite trail) under fixed position becomes `[3,2,1,0,0,...]` (secure) under rotation.
- `circulant` (secure under fixed position, `[3,2,1,0,0,...]`): rotation **breaks it** — becomes `[3,2,1,1,1,...]`, a *new* infinite trail that didn't exist before.

**Verdict**: confirms the plan's own warning that this "cuts both ways" — it's not a free security upgrade, it's a different design that needs its own from-scratch verification per candidate, same as the fixed-position design needs Algorithm 1/2. Since our actual NUMS-generated candidates are already at the fixed-position ceiling, rotation offers **no measured benefit** for the matrices we'd actually ship, and real risk of silently reintroducing a trail if applied carelessly to an arbitrary matrix. Not pursued further as a lightweight lever — the diffusion/R_P-reduction question (does touching every lane directly, once per `t` rounds, allow a *smaller* `R_P` even when the algebraic trail-length ceiling is unchanged?) is a distinct, not-yet-tested question or a real statistical-diffusion bound, not an algebraic one. Given Step 5.4/5.5's lesson, reducing `R_P` on this basis would need its own from-scratch interpolation/Gröbner bound re-derivation before trusting it, not an assumption.

### Step 5.7 — "Something more exotic": GMiMCHash2's tricks, then a lookup hybrid (user's idea, 2026-11-03)

**5.7a — GMiMCHash2's two tricks (SoK Sec 5.1.2, read in full from the primary PDF before implementing anything — good thing, since one of them would have broken the design):**

1. **`α = 2^k` S-box.** GMiMCHash2 uses this because GMiMC is a **Feistel** construction (Fig. 7): `F(x)=(x+c)^α` is applied to only one branch, and the round is invertible via the Feistel subtract-and-rotate structure regardless of whether `F` itself is injective — the paper's own point is that `F` does **not** need to be a bijection there. Our design is an **SPN** (Poseidon-style): in full rounds the S-box is applied directly to every lane with no Feistel structure to compensate, so the S-box **must** be a bijection (`gcd(α,p-1)=1`) for the permutation to be invertible at all. Since `p-1` is even for every prime field we use, any power of 2 shares a factor with `p-1` — adopting `α=2^k` would make the permutation **non-invertible**, i.e. broken, not lighter. **Does not port.** Caught by reading the primary source before implementing, not after.
2. **`M_IO` input/output matrix** (Eq. 50, `P(x) = M_IO · R^(R) ∘ ... ∘ R^(1)(M_IO · x)`). This one is structurally portable to any SPN — no Feistel dependency. But its stated purpose (Sec 5.1.2, after Table 4) is explicitly "so that a DRL Gröbner [basis] **can be computed** with a change of coordinates, **but with minimal impact on overall performance**" — it's a tool for making the *designers'* own security analysis tractable, not a round-count or constraint-count reduction. Confirmed it doesn't move any of our cost numbers; not pursued as a lightweight lever, though worth remembering as a technique if we ever need to hand-verify a Gröbner-basis bound ourselves in Phase 5's write-up.

**Verdict for 5.7a: neither GMiMCHash2 trick makes our construction lighter.** One would have broken it; the other targets a problem (analytical tractability) we don't currently have.

**5.7b — Lookup hybrid (the actual "exotic" direction the SoK itself flags as most promising) — scoped, not yet built:**

Real cost to do this properly: our entire Phase 4 toolchain (`circom` 2.2.3 + Groth16/snarkjs, installed in Step 5.1) is **R1CS-only** and has no lookup-argument support. A real compiled benchmark needs a different backend entirely (Halo2, Plonky2, or a STARK system with native lookups) — a toolchain we have not installed, comparable in scope to the Rust/circom install in Step 5.1 but for an unfamiliar circuit API, not just a new compiler. Flagging this honestly before claiming a result: this step is **not yet built**, only scoped below.

Known reference numbers already gathered in the earlier deep-research pass (`research_notes/Mejoras al diseño HADES Poseidon/sbox_cost_comparison.md`): Monolith vs. Poseidon on STARK/Plonky2 — proving 3.49ms vs. 6.23ms, verification 0.63ms vs. 1.12ms, proof size 113kB vs. 70kB (Monolith faster to prove/verify, larger proofs); Reinforced Concrete's lookup-based "Bars" layer alone consumes ~75% of its own PlonKup constraints (two independently corroborated sources). These are published numbers for the *pure* lookup-only designs, not for a hybrid.

Proposed next action, in order (so we validate the idea before paying for new tooling): (1) model a hybrid *algebraically* first, inside our existing Python tooling — represent a "lookup round" in `analysis/degree.py`'s tracker as a degree-breaking round (a lookup table's output has no low-degree polynomial relationship to its input, unlike every round type we've modeled so far) and check whether replacing some of our algebraic rounds with this round type lets `finite_trail_scanner.py`'s criterion pass at a smaller total round count; only (2) if that looks genuinely favorable, install a lookup-capable backend and get a real compiled number, the same discipline Step 5.1 followed for circom.

**(1) attempted and found invalid, not just unfavorable.** Modeled a "lookup round" as contributing degree `p-1` (a lookup table realizes an arbitrary function, whose algebraic normal form generically has degree near `p-1`, unlike our fixed-low-degree `x^α` S-box) in a multiplicative degree-bar tracker. Result: replacing even a **single** partial round out of 57 with a "lookup round" anywhere makes the naive degree bound exceed the field size `p`, "clearing" the naive check — which the model then reports as true for cutting *56 of 57* partial rounds down to just 1 lookup round. That's obviously not a real security argument: an attacker facing that construction would simply ignore the lookup round and attack the one remaining (near-trivial) algebraic prefix directly. The naive multiplicative degree-bar model has **no way to represent an attacker splitting the problem at the lookup boundary and attacking the algebraic remainder separately** — which is exactly the real attack a reviewer would try first, and exactly the kind of argument Reinforced Concrete/Monolith's own security proofs have to make carefully, not casually.

**Conclusion: the cheap shortcut doesn't work, confirmed by a vacuous result rather than assumed.** A real answer needs either (a) a close reading of how Reinforced Concrete/Monolith formally argue hybrid lookup+algebraic security (a literature task, not a code extension — our existing tooling's degree-bar abstraction is fundamentally the wrong model for this question), or (b) skip straight to (2): install a real lookup-capable backend and measure a compiled hybrid circuit directly, no shortcut. Treating the lookup hybrid as a flagged, scoped **future-work item** for the paper rather than a result to claim this session — the lightweight-lever exploration (Steps 5.4-5.7) is otherwise exhausted: field size is the one real, verified win; α, R_F-at-BN254, S-box rotation, and both GMiMCHash2 tricks were all tried and found to not help.

### Step 5.9 — Tested Plonky3 (2026-11-03): round numbers are fine, but the external matrix uses the exact vulnerable Kronecker order

Cloned `Plonky3/Plonky3` (Polygon's STARK proving stack — Goldilocks/BabyBear/KoalaBear fields, used underneath FRI/uni-stark). Two separate checks, two different outcomes:

**Round numbers (`poseidon2/src/round_numbers.rs`) — clean, cross-validated.** Plonky3's own precomputed table gives `(t=16, α=5, 64-bit field)`: `R_F=8, R_P=27`. Merz & García's "not considered by Poseidon's designers" concern about this parameter set does not show up as a round-count deficiency — by the most current recomputation available (SoK, Sept. 2026), Plonky3's numbers are correct.

**External matrix structure (`poseidon2/src/external.rs`) — uses the exact vulnerable order, confirmed three ways.** Reading the actual `mds_light_permutation` code (lines 135-153) for `WIDTH ∈ {4,8,12,16,20,24,32}`: "First, we apply `M_4` to each consecutive four elements of the state... Now, we apply the outer circulant matrix" — `M_4` applied to each 4-wide chunk **first** (inner), then an outer sum-based mixing **second** (outer). In Kronecker terms this is exactly `M_ε = P_{t/4} ⊗ M_4` — the order Merz & Rodríguez García's attack needs, **not** their own recommended fix (`M_4 ⊗ P_{t/4}`). Confirmed computationally, not just by code-reading:
1. Plonky3's `HLMDSMat4` ("the matrix used by the Horizon Labs implementation", `external.rs` line 76) is **byte-identical** to the `M_4` `analysis/tensor_matrix.py` already encodes from the attack paper itself.
2. Built the exact 16×16 `M_ε` Plonky3's code produces (`P_4 ⊗ M_4` via `analysis/tensor_matrix.py::external_matrices`) and confirmed the `(X,−X,0,...,0)` attack shape **survives** it (`_is_block_x_neg_x` → `True`).
3. Our **general**, Kronecker-structure-agnostic Algorithm 2 detector (`scan_full_round_matrix`, built in Step 2.2 and never told anything about tensor products) independently flags this exact matrix `any_suspicious=True` — the same detector that correctly found nothing in circomlib's unrelated, non-tensor-structured matrix (Step 5.8), which is itself useful evidence the detector isn't just flagging everything.

**What we did NOT verify, stated precisely so this isn't overclaimed**: whether this is *practically* exploitable depends on Plonky3's actual sponge capacity / digest size (`c`/`d`) in each real usage site — Merz & García's own countermeasure note says their exhibited attacks don't apply when `c ≥ t/4` or `d ≥ t/4`, regardless of matrix order. The rate/capacity split isn't set in `poseidon2.rs` itself; it's configured per call site (`fri/`, `uni-stark/`), which we did not chase down this pass. **Conclusion stated at the correct confidence level: the structural precondition for the Merz & García attack class is confirmed present in real, actively-used production code (not just a hypothetical); whether any specific deployed configuration's `(c,d)` happens to still clear their stated safe threshold is a separate, unverified question.** This is exactly the kind of precise, appropriately-hedged finding Step 5.8 set out to look for — a real external validation of Algorithm 2, independent of our own confirmation bias on our own candidates.

### Step 5.10 — Tested arkworks-rs (2026-11-03): no code gap this time, a *documentation-vs-implementation* gap instead — arguably the stronger finding

Cloned `arkworks-rs/crypto-primitives`. Structurally very different from both prior targets: it ships **no fixed, pre-audited matrix constants at all** (no `poseidon_constants`-style file like circomlib's) — every consumer calls a parameter *generator* (`find_poseidon_ark_and_mds`, `sponge/poseidon/traits.rs`) with their own `(prime_bits, rate, full_rounds, partial_rounds)` and gets a freshly-built Cauchy matrix + Grain-LFSR constants back. This matches Merz & García's own description of this target exactly (eprint 2026/306 Sec 6.1): "uses a 64 bit prime with `t=24`... an MDS matrix is implemented instead" — i.e. not Poseidon2's tensor-structured `M_ε`, so the Plonky3-style Kronecker-order check (Step 5.9) doesn't even apply here; this is Poseidon1-style, one dense matrix for everything, same shape as circomlib and our own repo's design.

**What we found instead, reading the actual code (`traits.rs` lines 131-145):**

```rust
// a qualifying matrix must satisfy the following requirements
// - there is no duplication among the elements in x or y
// - there is no i and j such that x[i] + y[j] = p
// - the resultant MDS passes all the three tests

let xs = lfsr.get_field_elements_mod_p::<F>(rate + 1);
let ys = lfsr.get_field_elements_mod_p::<F>(rate + 1);
for i in 0..(rate + 1) {
    for j in 0..(rate + 1) {
        mds[i][j] = (xs[i] + &ys[j]).inverse().unwrap();
    }
}
```

**None of the three stated checks are implemented.** No duplication check on `xs`/`ys`; no explicit `x[i]+y[j]=0` guard (the `.unwrap()` would panic in that case rather than silently misbehave, so that specific failure mode is at least loud, not silent); and critically, **"the resultant MDS passes all the three tests" is asserted in a comment with zero corresponding code** — confirmed via `grep` across the whole `sponge/poseidon/` directory: no function containing "check", "verify", "secure", "invariant", or "irreducib" exists anywhere in it.

**The deeper point, beyond the comment/code mismatch itself**: even a *fully correct* implementation of the three stated checks (no duplicates, no zero-sum pairs) would **still not be a GRS21-style invariant-subspace-trail check, an Algorithm-2-style full-round check, or anything resembling either** — they're basic well-formedness conditions for a Cauchy construction (which guarantees the MDS/branch-number property essentially for free, independent of these three checks), not a security argument against the attack class this whole research plan is about. **arkworks-rs's parameter generator provides zero automated protection against generating a GRS21-vulnerable or Vitto-vulnerable matrix for any custom `(t, field, R_F, R_P)` a downstream project chooses** — unlike the Ethereum Poseidon Initiative's own `poseidon-tools` verifier (Step "internal_matrix_criteria" research notes), which does implement exactly these checks (`_check_minpoly`, `_algorithm_1/2/3`).

**Scope, stated precisely**: this is a **documentation/implementation gap finding**, verified by reading the code directly, not a demonstrated break of any specific deployed matrix — we did not re-implement the Grain LFSR in Python to generate and test a concrete matrix for a specific `(t, field)` a real downstream project (Aleo/Mina/Aztec/Celo, all arkworks consumers) actually uses, which is the natural follow-up if this needs to go from "the generator has no safety net" to "project X's specific instance is vulnerable." **Arguably the more directly citable finding of Steps 5.8-5.10**: it needs no hedging about practical exploitability (unlike Plonky3's `(c,d)`-dependent caveat) — the absence of any invariant-subspace-trail check in a widely-depended-on parameter generator is true regardless of which specific `(t, field, R_F, R_P)` any downstream project picks.

**Summary across all three real-world targets (Steps 5.8-5.10)**: circomlib (fixed, audited constants) — clean. Plonky3 (fixed constants, tensor-structured `M_ε`) — structurally matches the known-vulnerable Kronecker order, practical exploitability unconfirmed. arkworks-rs (no fixed constants, generate-your-own) — no invariant-subspace-trail check exists in the generator at all, a gap our own tooling is a direct, pluggable answer to.

User pushed again on "is there really nothing more to make our own construction lighter" after Steps 5.4-5.7 seemed to exhaust the obvious levers. Re-examining what Steps 5.1-5.10 actually optimized: every candidate this whole plan scored (`poseidon2_sparse` and friends) only ever made `M_I` (the partial-round matrix) cheap — `M_full` (the full-round matrix, paid `R_F` times, each time with a nonlinear S-box on *every* lane) was **always** a dense NUMS matrix (`nums_full_round_matrix`), never optimized. Poseidon2's own design optimizes *both* matrices via the tensor/Kronecker structure (Step 1.4/5.9); we had only ever borrowed the attack/defense mechanics of that structure, never its efficiency benefit.

Built it for `M_full` using the SAFE factor order confirmed in Step 5.9 (`M_4 ⊗ P_{t/4}`, the swap Plonky3 itself does *not* use) at `t=16` (Vitto's own instance width, `α=3, R_F=8, R_P=20`):

- **Security**: `unified_criterion(M_I=poseidon2_sparse, M_full=M_4⊗P_4, ...)` → `passed=True`. Matches Step 5.9's own `scan_full_round_matrix` confirmation that the safe order isn't flagged.
- **R1CS cost (real `circom` compile, not just the formula)**: `296` non-linear + `596` linear = `892` total — compiled a second circuit with the old dense `M_full` at the identical `(t,α,R_F,R_P)` as a direct control: **byte-identical**, `296`/`596`/`892`. Reconfirms Step 5.2's "R1CS doesn't care about matrix structure" finding, now also at `t=16`, not just `t=3`.
- **Real multiplicative cost — the actual win, and a correction to our own cost model along the way**: `poseidon.matrix_search.mul_complexity()` counts non-`{0,1}` entries of the fully-*expanded* `t×t` matrix — a fair proxy for a matrix you'd multiply naively, but **wrong** for a tensor-structured matrix, which real implementations (Plonky3's own `mds_light_permutation`, read directly in Step 5.9) compute via a fast block algorithm: apply the dense `4×4` `M_4` to each of `t/4` blocks, then an **outer mix that is pure addition** (every `P_{t/4}` entry is `1` or `2`, i.e. free). Naive entry-count for `t=16`: `184`. Real fast-algorithm count (`analysis/tensor_matrix.py::mul_complexity_tensor`, added this step): `4 blocks × 10 (mul_complexity of M_4 alone) = 40` — **4.6x apart**. Recomputing the full permutation's `mul_complexity_total` with the honest fast-algorithm number: `8×40 + 20×16 = 640`, vs. `8×256 + 20×16 = 2368` for the original all-dense design — **a 73% reduction**, not the `24.3%` the naive (but still-positive) entry-count comparison gave first.

**Caveat, same shape as every other lever in this plan**: this only applies at `t` divisible by 4 (Poseidon2(b)'s quadruple structure) — doesn't apply to this repo's own `t=3` default at all. At `t=16` (or `8,12,20,...`) it's real, verified by compile and by the unified security criterion, and it's the first lever found that improves `M_full` specifically rather than `M_I` — everything through Step 5.7 only ever touched the partial-round side.
### Step 5.12 — Exhaustive attack against the final candidate at its real target scale, with a direct comparison to Skipping Class (2026/306) and Slipway (2026/1579) (2026-11-03, user's explicit request)

The user asked for one exhaustive pass against the ACTUAL final design, with a reference table against the two primary attack papers. Doing this surfaced two real bugs in our own tooling before any numbers could be trusted, and one genuine (but ultimately benign) field-dependent finding worth documenting for the paper.

**Two field-genericity bugs found and fixed while building the battery, both the same shape:** `analysis/trail_freeze.py` and `analysis/tensor_matrix.py` still had module-level `from poseidon.field import Fp` (BN254) left over from before the rest of the codebase (Step 5.9/5.10's field-generalization push) was made field-generic — unlike `poseidon/linalg.py`, `poseidon/polynomial.py`, `poseidon/matrices.py`, `poseidon/constants.py`, which all infer the field from the data they're given. Both modules happened to look correct for months of testing because every prior use was at `t=3`/BN254, the hardcoded field — the bug only manifests when a different field is actually passed in.
  - **How it was caught**: ran `run_partial_rounds_symbolic` directly on a KoalaBear direction `d ∈ K_4(M_I)` and got `entering_degrees` showing the freeze breaking after round 0, not round 4 — contradicted a pure linear-algebra check (`(M_I^j·d)[0]` for `j=0..4` via `finite_trail_space`/`mat_mul` directly) that confirmed the direction genuinely has zero contribution to the active coordinate through `j=3` and first becomes nonzero at `j=4`, exactly as `dim K_4(M_I)=12` predicts. Cross-checking the surprising result against an independent computation path (same discipline as every other bug caught in this plan) isolated the fault to `_linear_layer_symbolic`: it allocated its zero-accumulator as the hardcoded BN254 `Fp(0)` instead of inferring the field from the actual state polynomials, silently mixing a BN254-typed zero into a KoalaBear computation the moment the linear layer ran.
  - **Fix**: `_scalar_poly_mul` and `_linear_layer_symbolic` now infer `field = type(poly[0])` / `type(state_polys[0][0])` from the data, matching the pattern everywhere else; `verify_lemma1_freeze` and `check_no_accidental_landing` gained an explicit `field=Fp` parameter (default preserves exact prior BN254 behavior) so they generalize instead of silently assuming BN254. Same fix applied to `analysis/tensor_matrix.py`'s `p_matrix`, `m4_matrix`, `external_matrices`, `build_x_neg_x_vector`, `mul_complexity_tensor` — identical hardcoded-`Fp` shape, caught proactively once the first instance was found, before it caused a second silent wrong answer.
  - **Regression check**: re-ran the original `t=3`/BN254 Step 1.2 and Step 1.4/5.11 results byte-for-byte after the fix — `verify_lemma1_freeze` still gives `[0,0,1,5]`/frozen=True/jump=True, `check_no_accidental_landing` still gives `[1,5,25]`/match=True, `demo_eigenvector_structure`/`demo_full_round_survival` still both `True`, `mul_complexity_tensor(t=16, BN254)` still `40` — zero regressions, confirming the bug was genuinely new-field-only, not a latent error in any previously-published number in this file.
  - **Re-run at KoalaBear scale with the fix**: `entering_degrees=[0,0,0,0,1,3]` for the adversarial direction in `K_4(M_I)` — frozen for exactly 4 rounds, jumps at round 4, matching the `dim K_4=12` prediction exactly, same mechanism as the `t=3` case, now also confirmed at the field/width Vitto's own paper actually targets.

**A genuine field-dependent finding, investigated and resolved as a benign false positive, not a break:** `scan_full_round_matrix` (Algorithm 2's static structural half) flags `any_suspicious=True` for the *safe*, swap-fixed `M̄_ε = M_4 ⊗ P_4` matrix at `t=16`/KoalaBear — the same matrix Step 1.4/5.9 already confirmed clean (`any_suspicious=False`) at BN254. This is not a contradiction: which irreducible factors `χ(M̄_ε)` splits into over `F_p` is field-dependent by definition (factorization behavior depends on the prime), and at KoalaBear's prime two of the factors are irreducible quadratics (vs. 8 linear factors at BN254), producing a genuinely different, 6-dimensional invariant subspace with a `max_contiguous_zero_run=6 ≥ t/4=4` — the static heuristic's threshold trips.
  - **Did not stop at the static flag** — applied the same dynamic test Step 1.4 used to confirm the *real* attack originally (`demo_full_round_survival`): pushed a basis vector of the flagged subspace through one real full round (S-box + `M̄_ε`). First attempt with a basis vector whose entries happened to be exactly `±1` gave a misleadingly clean-looking survival — but `(±1)^α = ±1` trivially for any odd `α`, a degenerate test that proves nothing. Re-ran with a **generic** (non-`±1`) point in the same subspace: the S-box step preserves the zero/nonzero pattern (true of *any* vector under a pointwise power map — zero stays zero, nonzero stays nonzero, not special to this subspace), but after the full round (S-box **then** `M̄_ε`) the vector went to **full weight, 16/16 nonzero** — the subspace does not survive a real nonlinear round at all for a generic element.
  - **Root cause of the false positive**: Merz & García's actual exploit needs the specific `(q, −q, 0, ..., 0)` shape, where the odd-`α` identity `(−q_i)^α = −(q_i^α)` holds for *every* `q_i`, so the negation relationship between the two active blocks survives the S-box for *any* `q`, not just special values. Our KoalaBear-only subspace's basis vectors instead have **identical** (not negated) active blocks (`(q, 0, q, 0)`, not `(q, −q, 0, 0)`) — there is no reason that structure should be preserved by a nonlinear map, and empirically it isn't. `scan_full_round_matrix`'s contiguous-zero-run check is a **necessary-looking but not sufficient** condition for the actual exploit; it correctly finds every `M`-invariant subspace (that part is linear algebra, guaranteed correct) but cannot by itself tell a negation-compatible (exploitable) subspace from an identical-block (inert) one.
  - **Conclusion, now resting on the dynamic check, not just the static one**: the swap-order countermeasure remains genuinely effective at KoalaBear scale too — confirmed by the same no-accidental-landing full-round test (`[1,3,9]` matching naive `α^round` growth exactly, no freeze, Item [7] below). The static scanner's `any_suspicious=True` here is logged as a documented false-positive case, not retracted as wrong (the subspace it found is real), with the fix being procedural: **never report `scan_full_round_matrix`'s flag as a finding on its own — always pair it with a one-round nonlinear survival check** before concluding exploitability. Worth stating explicitly in the paper's §4 criterion as a methodological lesson, since it is exactly the kind of overclaim a reviewer would catch.
